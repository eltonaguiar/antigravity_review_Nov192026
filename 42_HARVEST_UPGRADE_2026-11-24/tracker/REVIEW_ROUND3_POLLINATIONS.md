1. **(A)** The “v_pick_latest_mark” view still nets a *single* mark per pick but does not enforce that the **selected** mark is the *latest* by a proper windowing clause. It simply self‑joins on `MAX(mark_date)`, which can still pull an older mark if two marks share the same `mark_date`. The view should use `ROW_NUMBER() OVER(PARTITION BY pick_id ORDER BY mark_date DESC)` and filter `rn=1`.  
2. **(B)** To deduce an honest effective sample size when 30 strategies issue the same BTC/USDT trade, the schema must record **strategy identifiers** alongside each pick and **aggregate only unique (pick_id, strategy_id)** combinations. This is best kept in a **derived table or view** (`v_unique_picks`) rather than a raw column because the overhead of updating a column for every pick is error‑prone and unnecessary.  
3. **(C)** Implement a **CHECK constraint** on `marks` that `days_held BETWEEN horizon_ref.min_days AND horizon_ref.max_days` *and* `days_held <= max(horizon_ref.max_days)` for the latest mark of each pick. This stops out‐of‑horizon marks from ever being counted.  
4. **(D)** The sixth fix – adding `screened_candidate` with a three‑state decision and `rule_hash` – is pure theatre; it adds no enforcement or analytic value to the core pick/mark logic.
